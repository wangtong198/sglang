# 07 调度器与 KV 缓存

调度器是 `python/sglang/srt/managers/scheduler.py` 的 `Scheduler`。KV 的字节布局在 `mem_cache/`，调度器只持有池和树的引用。

## 事件循环

`run_event_loop` 调 `dispatch_event_loop`，再按配置选一个循环。普通循环 `event_loop_normal` 的一轮是：

1. `ingest_requests`：ZMQ 非阻塞收 `TokenizedGenerateReqInput` 等。
2. `get_next_batch_to_run`：从 waiting / running 选出下一批。
3. `run_batch`：`TpModelWorker.forward_batch_generation`。
4. `process_batch_result`：采样、grammar、把 token 交给 `SchedulerOutputStreamer`。

`event_loop_overlap` 把第 4 步的 CPU 工作和下一轮的 GPU 前向叠在一起。PP、PD、MLX 有自己的循环，入口仍是 `dispatch_event_loop`。

`ForwardMode`（`model_executor/forward_batch_info.py`）决定这一批在 GPU 上算什么：

| 枚举 | 含义 |
| --- | --- |
| `EXTEND` | 预填充。序列开头的 KV 可能已经在 radix 里，只算未命中的后缀 |
| `DECODE` | 每个请求产出 1 个 token |
| `MIXED` | chunked prefill 时同一批里既有 extend 也有 decode |
| `IDLE` | DP attention 下这个 worker 这一轮没有序列。集合通信仍要参加，所以不能直接跳过进程 |
| `TARGET_VERIFY` | 投机解码里目标模型验证 draft |
| `DRAFT_EXTEND_V2` | 草稿模型的 extend |
| `PREBUILT` | PD 的 decode 侧，KV 已经从 prefill 传过来 |
| `SPLIT_PREFILL` | PD 复用时拆开的 prefill |
| `DLLM_EXTEND` | 扩散语言模型 |

`is_extend` 把 `EXTEND`、`MIXED`、`TARGET_VERIFY`、`SPLIT_PREFILL`、`DLLM_EXTEND` 都当成“要写一段 KV”。`DRAFT_EXTEND_V2` 默认不算，除非调用方显式打开。

## 调度策略

`managers/schedule_policy.py` 的 `SchedulePolicy`。CLI 字段是 `schedule_policy`（05 的调度一节）。策略分两组：

| 枚举 | 值 | 看不看前缀树 |
| --- | --- | --- |
| `CacheAwarePolicy.LPM` | `lpm` | 看。优先最长前缀命中 |
| `CacheAwarePolicy.DFS_WEIGHT` | `dfs-weight` | 看 |
| `CacheAwarePolicy.HRRN` | `hrrn` | 看。按 token 老化做最高响应比 |
| `CacheAwarePolicy.SHORTEST_PREFILL_FIRST` | `shortest-prefill-first` | 看 |
| `CacheAgnosticPolicy.FCFS` | `fcfs` | 不看 |
| `CacheAgnosticPolicy.LOF` | `lof` | 不看。优先已经生成得比较长的请求 |
| `CacheAgnosticPolicy.RANDOM` | `random` | 不看 |
| `CacheAgnosticPolicy.ROUTING_KEY` | `routing-key` | 不看树，看 running batch 里 routing key 的频率 |

`_validate_and_adjust_policy` 会在树被关掉时把 cache-aware 策略换掉。请求上的 `priority` 由 `enable_priority_scheduling` 和 `schedule_low_priority_values_first` 决定排序方向。

选出一批之后还要受这些预算约束（字段在 `schedule` 命名空间）：

| 字段 | 作用 |
| --- | --- |
| `max_running_requests` | 同时在跑的请求上限。V4 的模型 hook 在未设置时可能把它改成 256 |
| `chunked_prefill_size` | 一轮 extend 最多吃多少 token。`-1` 表示关闭。DP attention 时再除以 `attn_dp_size` |
| `schedule_conservativeness` | 估计还能塞多少 decode。打开 attention DP 时乘 0.3 |
| `max_prefill_tokens` | 预填充 token 上限 |

## KV 池的两张表

`KVCacheConfigurator._init_pools` 建的是：

| 对象 | 作用 |
| --- | --- |
| `req_to_token_pool` | 请求槽位 → token 在 KV 池中的下标。一个请求一条逻辑序列 |
| `token_to_kv_pool` | 真正的 K/V 张量。页大小对 V4 被 override 成 256 |
| `token_to_kv_pool_allocator` | 按页申请和归还 |

选池的分支（`kv_cache_configurator.py` 的 `_build_token_to_kv_pool`）：

| 条件 | 池 |
| --- | --- |
| `is_dsv4_model` | `DeepSeekV4TokenToKVPool`（NPU 上是 `DSV4NPUTokenToKVPool`） |
| MLA + hybrid SWA | hybrid MLA/SWA 池 |
| MLA + DSA | `DSATokenToKVPool` |
| 普通 MLA | `MLATokenToKVPool` |
| 默认 MHA | `MHATokenToKVPool` 或 page-major 变体 |
| `enable_unified_memory` | unified mamba/SWA 池。DeepSeek-V4 被排除 |

容量不是 config 里写死的。`_profile_available_bytes` 在权重加载之后读空闲显存，减去 `mem_fraction_static` 留出的部分和多模态预留，再换成能放下的 token 页数。所以同一份 V4.1-Flash，144GB 卡和 192GB 卡的 `max_total_num_tokens` 不同，不必在 CLI 里猜。

V4.1 的层不是同一种 KV。`compress_ratios[layer]` 为 0 的层不压缩，为 1 或 2 的层按这个比例写压缩状态。`sliding_window = 128` 的层只留窗口。池的布局要同时满足这三种层，这就是不用普通 MHA 池的原因。`assert self.compress_ratio in (0, 1, 2, 4, 128)` 在层初始化时执行，config 里出现别的数会在建模型时失败，而不是在第一条请求时失败。

## 请求对象

运行中的请求是 `schedule_batch.py` 的 `Req`，不是 HTTP 的 `GenerateReqInput`。tokenizer 把后者收成 `TokenizedGenerateReqInput`，`handle_generate_request` 再建成 `Req`。`Req` 上和缓存相关的状态包括：已经匹配的前缀长度、fill 的位置、grammar 状态、采样参数、LoRA id。请求结束时 `release_kv_cache`（`mem_cache/common.py`）调用 `tree_cache.checkpoint`，把这条序列的 KV 页交回 radix，而不是立刻 free 掉仍可能被别的请求命中的页。

## DP attention 下的空转

`ForwardMode.IDLE` 存在，是因为 MoE all-to-all 和 TP 集合通信要求每个 rank 都进 kernel。某个 attention DP 组这一轮没有请求时，scheduler 仍要发出一个空 batch，让别的组的 expert dispatch 有对端。跳过这个 rank 的 forward 会让别的节点挂在通信上。
