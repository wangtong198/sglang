# 07 调度器与 KV 缓存

调度器是 S9，也负责 S5/S6 的初始化。类是 `managers/scheduler.py` 的 `Scheduler`。KV 字节在 `mem_cache/`，调度器持有池和树的引用。

## 一轮循环做完什么

`run_event_loop` → `dispatch_event_loop`。普通路径 `event_loop_normal`：

| 步 | 函数 | 输入 | 做完 | 输出 |
| --- | --- | --- | --- | --- |
| 1 | `ingest_requests` | ZMQ 上的 `TokenizedGenerateReqInput` | 建成 `Req` 或推进 grammar 队列 | waiting 队列变长 |
| 2 | `get_next_batch_to_run` | waiting + running + 树的匹配结果 | 按策略和预算选出一批 | `ScheduleBatch` |
| 3 | `run_batch` | `ScheduleBatch` | 交给 worker | GPU 上的 logits |
| 4 | `process_batch_result` | logits | 采样、grammar mask、判断结束 | `BatchTokenIDOutput` 流向 S11 |

`event_loop_overlap` 把第 4 步的 CPU 和第 1–2 步的下一次准备叠在上一次 GPU 前向后面。PP、PD、MLX 换循环，入口仍是 `dispatch_event_loop`。

`ForwardMode` 是这一轮的合同，定义在 `forward_batch_info.py`：

| 值 | 本轮完成的工作 |
| --- | --- |
| `EXTEND` | 预填充。开头的 KV 可能已在 radix 里，只算未命中后缀 |
| `DECODE` | 每个请求一个新 token |
| `MIXED` | chunked prefill 时 extend 与 decode 同批 |
| `IDLE` | attention DP 这组没有请求，但仍参加集合通信 |
| `TARGET_VERIFY` | 目标模型验证草稿 |
| `DRAFT_EXTEND_V2` | 草稿模型 extend |
| `PREBUILT` | PD decode，KV 已从 prefill 传来 |
| `SPLIT_PREFILL` | PD 复用时拆开的 prefill |
| `DLLM_EXTEND` | 扩散语言模型 |

`is_extend` 把 EXTEND、MIXED、TARGET_VERIFY、SPLIT_PREFILL、DLLM_EXTEND 当成「要写一段 KV」。`DRAFT_EXTEND_V2` 默认不算。

## 策略

`SchedulePolicy`（`schedule_policy.py`）在第 2 步排序。

| 枚举 | 值 | 看不看树 |
| --- | --- | --- |
| `CacheAwarePolicy.LPM` | `lpm` | 看，优先最长前缀 |
| `CacheAwarePolicy.DFS_WEIGHT` | `dfs-weight` | 看 |
| `CacheAwarePolicy.HRRN` | `hrrn` | 看，按 token 老化 |
| `CacheAwarePolicy.SHORTEST_PREFILL_FIRST` | `shortest-prefill-first` | 看 |
| `CacheAgnosticPolicy.FCFS` | `fcfs` | 不看 |
| `CacheAgnosticPolicy.LOF` | `lof` | 不看，优先已经生成得较长的 |
| `CacheAgnosticPolicy.RANDOM` | `random` | 不看 |
| `CacheAgnosticPolicy.ROUTING_KEY` | `routing-key` | 不看树，看 running 里 routing key 的频率 |

树被关掉时，`_validate_and_adjust_policy` 会把 cache-aware 策略换掉。`priority` 的方向由 `enable_priority_scheduling` 和 `schedule_low_priority_values_first` 决定。

预算（S2 可能改过声明值）：

| 字段 | 作用 |
| --- | --- |
| `max_running_requests` | 同时在跑的请求数。V4 hook 在未设置时可能改成 256 |
| `chunked_prefill_size` | 一轮 extend 的 token 上限。`-1` 关。attention DP 时再除以组数 |
| `schedule_conservativeness` | 估计还能塞多少 decode。attention DP 时乘 0.3 |
| `max_prefill_tokens` | 预填充 token 上限 |

## `Req`：单请求在 S9 的状态

构造在 `schedule_batch.py` 的 `Req`。HTTP 的 `GenerateReqInput` 到不了这里，中间经过 `TokenizedGenerateReqInput`。

| 成员 | 含义 |
| --- | --- |
| `rid` | 请求 id。`cache_request_handle` 带 attempt |
| `origin_input_ids` | 分词结果。`origin_input_ids_unpadded` 是图像 padding 之前的序列 |
| `output_ids` | 已生成 token，只追加。原地改长度会破坏 `refresh_fill_ids` |
| `full_untruncated_fill_ids` | 输入加输出。本轮 extend 的区间是 `[prefix_len, extend_end)` |
| `sampling_params` | 已经 `normalize` 的采样参数 |
| `kv` | `ReqKvInfo`，见下表 |
| `lora_id` / `session_id` / `cache_salt` / `extra_key` | 前缀键的命名空间 |
| `bootstrap_host/port/room` | PD 配对 |
| `routed_dp_rank` | 指定的 attention DP 组 |
| `grammar` 相关队列 | 约束解码还没编译完时不进 GPU |
| `require_reasoning`、`_is_reasoning_over` | 思考阶段是否结束。解析器主要在 S7/S11，这里留计数 |

### `ReqKvInfo`

设备上属于这个请求、又不在前缀树保护范围内的 KV。

| 成员 | 含义 |
| --- | --- |
| `req_pool_idx` | `req_to_token` 的行。`holds_kv` 就是它非空 |
| `cache_protected_len` | `[0, 这里)` 归树所有（匹配到或已插入） |
| `cache_inserted_len` | 已经插入树的长度，避免同一节点计两次命中 |
| `kv_committed_len` | 内容已提交的位置，不超过已分配长度 |
| `kv_allocated_len` | 已分配长度 |
| `swa_evict_floor` | `[0, 这里)` 不做窗口驱逐 |
| `component_evicted_seqlens` | 按组件记录已驱逐位置 |
| `mamba_pool_idx` 及 ping-pong 字段 | 线性注意力状态，和 KV 页分开 |

`swa_dead_lo` 计算这个请求自己可以释放的 SWA 下界：不低于树保护的前缀，也不低于 `swa_evict_floor`，再按页对齐。

## `ScheduleBatch`：一轮的容器

| 成员 | 谁读 | 含义 |
| --- | --- | --- |
| `reqs` | 调度器和 `ForwardBatch` | 本批请求 |
| `req_to_token_pool` / `token_to_kv_pool_allocator` / `tree_cache` | S6 建好后一直引用 | 三份全局资源 |
| `chunked_req` | chunked prefill | 还没写完的那条 |
| `decoding_reqs` | MIXED | 和 chunk 预填充搭车的 decode |
| `inner_idle_batch` | attention DP | 空转批 |
| `input_ids` | 拷进 `ForwardBatch` | 本轮 token |
| `batch_is_full` | 第 2 步 | 满了就跳过「还能不能再塞 prefill」的检查 |

## `ForwardBatch`：S10 真正看见的

由 `TpModelWorker.forward_batch_generation` 从 `ScheduleBatch` 造出。必填：`forward_mode`、`batch_size`、`input_ids`、`req_pool_indices`、`seq_lens`、`out_cache_loc`、`seq_lens_sum`。

| 成员 | 含义 |
| --- | --- |
| `req_pool_indices` | 请求在 `req_to_token` 里的行 |
| `out_cache_loc` | 本轮新 KV 写入 token 池的下标 |
| `kv_loc_plan` | 这一迭代各子池的写入计划。V4 有压缩池和 SWA 池，不能只有一个下标空间 |
| `out_cache_loc_is_physical` | 下标是物理页还是虚拟页，由 `KVLocPlan.bind` 设置 |
| `origin_out_cache_loc` | NPU DCP 把位置改成本地之前的全局槽 |

## 池怎么被选出来

S6 的 `KVCacheConfigurator._init_pools`：

| 条件 | 池 |
| --- | --- |
| V4 | `DeepSeekV4TokenToKVPool`（NPU 是 `DSV4NPUTokenToKVPool`） |
| MLA + hybrid SWA | hybrid 池 |
| MLA + DSA | `DSATokenToKVPool` |
| 普通 MLA | `MLATokenToKVPool` |
| 默认 | `MHATokenToKVPool` 或 page-major |
| `enable_unified_memory` | mamba/SWA 统一池。V4 被排除 |

容量不是 config 里的常数。`_profile_available_bytes` 在权重加载后读空闲显存。同一份 V4.1-Flash，144GB 和更大的卡得到的 token 上限不同。

`compress_ratios[layer]` 为 0 的层不压缩，为 1 或 2 的层写压缩状态，`sliding_window=128` 的层只留窗口。层构造只接受 0、1、2、4、128，非法值在 S5 建层时失败，不会拖到第一条请求。

请求结束时 `release_kv_cache`（`mem_cache/common.py`）调用 `tree_cache.checkpoint`。页回到树里，而不是立刻 free。仍被别的请求锁住的前缀继续占着显存，这是 Radix 的目的，不是泄漏。08 写匹配和锁。
